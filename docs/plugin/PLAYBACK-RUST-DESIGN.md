# 재생 Rust 이전 설계안(D2 확장)

- 작성: 2026-11-10. 상태: **결정됨(2026-11-10), R1·R2·R3 구현(청취 확인 대기)**. 코드·저장 형식 변경 없음.
- 배경: D2(2026-11-07)는 "테이크 재생을 Rust 출력 엔진으로"였고, 2B에서는 TAKE 하나만 모니터 경로에 합쳤습니다. 반주·다른 테이크·스템·Bounce·메트로놈은 아직 WebView가 재생합니다.

## 1. 지금 구조

| 소리 | 재생 주체 | 시간 기준 |
| --- | --- | --- |
| 반주(WAV·MP3) | `PlayerEngine`(HTMLAudioElement, `preservesPitch`, 0.5~1.5배) | 이 재생기가 곡 시각의 기준 |
| 테이크·Freeze·스템·Bounce | `TakeMixPlayer`(레이어마다 HTMLAudioElement) | 반주 시각을 따라가고 500ms 넘게 어긋나면 seek |
| 메트로놈·카운트인 | WebAudio OscillatorNode | 반주 시각 |
| AmpliTube 테이크 1개 | Rust 모니터 출력 callback(`monitor_playback.rs`) | 반주 시각을 받아 시작 프레임 지정 |
| 입력 모니터 | Rust(CPAL 입력 → 링 → DSP → CPAL 출력) | 입력 stream 세대에 묶임 |

문제:
- 레이어끼리 샘플 단위 동기가 없습니다(문서에도 "보장하지 않음"). AmpliTube 테이크와 WebView 레이어는 출력 장치·지연이 달라 서로 어긋날 수 있습니다.
- 녹음 정렬은 JS가 보낸 시각 기준점(`audio/clock.rs`)에 의존합니다. Rust가 출력 프레임을 직접 알면 더 정확해집니다.
- WebView 출력은 Windows 기본 장치로, 모니터는 고른 장치(SSL 등)로 나갑니다.

## 2. 목표

Rust 재생 엔진 하나가 모든 믹스 레이어와 반주를 **같은 출력 callback에서 샘플 단위로** 섞습니다. 곡 시각은 그 엔진의 출력 프레임이 기준이 됩니다. JS는 명령을 보내고 위치를 읽는 화면이 됩니다. 녹음은 계속 DI만, 판정도 DI입니다.

## 3. 어려운 점

1. **MP3 반주**: Rust에 MP3 디코더가 없습니다. 새 의존성이 필요합니다(예: `symphonia` 순수 Rust, MPL-2.0. 배포 고지 절차 필요). 아니면 MP3일 때만 WebView 경로를 남깁니다.
2. **0.5~1.5배 연습 속도(음정 유지)**: 지금은 브라우저의 `preservesPitch`가 해 줍니다. Rust에서는 time-stretch가 필요합니다. 외부 라이브러리(C++ 포함 가능)를 쓰거나 WSOLA를 직접 구현해야 하고, 품질 확인은 사람 몫입니다. 가장 큰 작업입니다.
3. **출력 stream 분리**: 지금 모니터 출력은 입력 stream 세대에 묶여 있습니다. 입력 없이 재생만 하려면 "재생 출력 엔진"을 따로 두고, 입력 모니터가 그 엔진에 합류하는 구조로 바꿔야 합니다(`monitor.rs` 큰 수정).
4. **메모리**: 10분 stereo 반주를 f32로 풀면 약 230MB입니다. 믹스 준비 예산 512MiB에 반주가 들어가야 합니다.
5. **YouTube**: 외부 플레이어라 옮길 수 없습니다. YouTube 반주일 때는 지금 방식을 유지합니다.

## 4. 단계안(권장)

| 단계 | 내용 | 끝나면 |
| --- | --- | --- |
| R1 재생 출력 엔진 | 입력과 독립된 CPAL 출력 엔진. 입력 모니터는 이 엔진에 합류. 2B 클립 재생을 여기로 옮김 | 입력 없이도 Rust로 소리를 냄, 기존 모니터 동작 유지 |
| R2 1배속 네이티브 믹스 | WAV 반주·TAKE·Freeze·STEM·IMPORTED_STEM·RENDER를 Rust가 섞음(음량·mute·solo·재생·정지·seek·구간 반복). 곡 시각=출력 프레임. JS `PlayerEngine`에 "네이티브 모드" | 1배속 WAV 반주에서 모든 레이어 샘플 단위 동기 |
| R3 메트로놈·카운트인·녹음 정렬 | 클릭을 Rust에서 생성, 녹음 기준점을 출력 프레임으로 | 녹음 정렬이 JS 시각 의존에서 벗어남 |
| R4 MP3 | 디코더 의존성 추가(결정 필요) | MP3 반주도 네이티브 |
| R5 속도 변경 | time-stretch(결정 필요) | 0.5~1.5배도 네이티브 |

R4·R5 전에는 **MP3 반주이거나 1배속이 아니면 지금 WebView 경로로 자동 전환**합니다(기능 손실 없음). 네이티브 모드가 실패하면 같은 방식으로 되돌아갑니다.

## 5. 결정할 것

1. 범위: 위 단계안(1배속 WAV부터, 나머지는 WebView로 대체)으로 갈지, 처음부터 전부 옮길지.
2. 재생 출력 장치: 모니터와 같은 고른 장치로 통일할지(권장), Windows 기본 장치를 따를지.
3. R4 MP3: `symphonia` 추가 / MP3는 계속 WebView.
4. R5 속도: 나중에 따로 설계 / 지금 같이 결정.

### 결정(2026-11-10 사용자)

1. 범위: **단계안 R1 → R2 → R3**. MP3·배속은 WebView 경로로 자동 전환.
2. 출력 장치: **모니터와 같은 고른 장치**.
3. MP3: **계속 WebView**(새 의존성 없음).
4. 속도 변경(R5): 나중에 따로 설계.

## 5A. R1 구현 계획(2026-11-10)

R1은 화면에 아직 연결하지 않는 Rust 쪽 바탕입니다(화면 연결은 R2).

1. **재생 버스**(`src-tauri/src/audio/playback_bus.rs`, 순수 로직): stereo 보이스 여러 개(엔진 샘플레이트로 미리 맞춘 `Arc<[f32]>` 좌우, 곡 위의 시작 프레임, 음량), 재생·정지·이동·구간 반복, 현재 곡 프레임을 atomic으로 공개. 출력 callback에서 할당·잠금·해제를 하지 않습니다. 바뀐 보이스 묶음은 제어 쪽이 사본을 들고 있다가 callback이 놓은 뒤 해제합니다(2B `monitor_playback`과 같은 방식).
2. **입력 없는 출력**: 모니터 출력 stream을 입력 없이도 열 수 있게 합니다(재생만). 입력 모니터를 켜고 끌 때는 stream을 다시 만들고, 제어 쪽이 가진 보이스 묶음·위치·재생 상태로 버스를 새로 만들어 이어 갑니다(수십 ms 끊김 허용. callback 안에서 AmpliTube 삽입을 해제하지 않기 위함). 샘플레이트가 바뀌면 보이스를 다시 불러오라는 오류를 냅니다.
3. **출력 합성**: 버스 소리는 삽입(AmpliTube) 뒤에 더하고 자기 음량을 씁니다. 모니터 음량·Bypass와 무관합니다.
4. IPC 명령은 R2에서 화면과 함께 정합니다. R1은 Rust 단위 테스트로 검증합니다.

## 6. 바뀌지 않는 것

- 녹음 파일은 DI만, 판정 입력도 DI, 원본 파일은 읽기만 합니다.
- DB·MixDocument 저장 형식은 R1~R3에서 바꾸지 않습니다(IPC 명령만 추가).
- 실시간 AmpliTube는 인스턴스 하나(D3) 그대로입니다. 트랙별 다른 실시간 톤은 이 설계 범위 밖입니다.
