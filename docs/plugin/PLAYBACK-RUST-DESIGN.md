# 재생 Rust 이전 설계안(D2 확장)

- 작성: 2026-11-10. 상태: **결정됨(2026-11-10), R1·R2·R3 구현(청취 확인 대기)**. 코드·저장 형식 변경 없음.
- 배경: D2(2026-11-07)는 "테이크 재생을 Rust 출력 엔진으로"였고, 2B에서는 TAKE 하나만 모니터 경로에 합쳤습니다. 반주·다른 테이크·스템·Bounce·메트로놈은 아직 WebView가 재생합니다.

## 1. 지금 구조

| 소리 | 재생 주체 | 시간 기준 |
| --- | --- | --- |
| 반주(WAV·MP3) | `PlayerEngine`(HTMLAudioElement, `preservesPitch`, 0.5~1.5배) | 이 재생기가 곡 시각의 기준 |
| 테이크·Freeze·스템·Bounce | `TakeMixPlayer`(레이어마다 HTMLAudioElement) | 반주 시각을 따라가고 500ms 넘게 어긋나면 seek |
| 메트로놈·카운트인 | WebAudio OscillatorNode | 반주 시각 |
| AmpliTube 테이크 1개 | Rust 모니터 출력 callback(`monitor_playback.rs`) | 반주 시각을 받아 시작 프레임 지정 |
| 입력 모니터 | Rust(CPAL 입력 → 링 → DSP → CPAL 출력) | 입력 stream 세대에 묶임 |

문제:
- 레이어끼리 샘플 단위 동기가 없습니다(문서에도 "보장하지 않음"). AmpliTube 테이크와 WebView 레이어는 출력 장치·지연이 달라 서로 어긋날 수 있습니다.
- 녹음 정렬은 JS가 보낸 시각 기준점(`audio/clock.rs`)에 의존합니다. Rust가 출력 프레임을 직접 알면 더 정확해집니다.
- WebView 출력은 Windows 기본 장치로, 모니터는 고른 장치(SSL 등)로 나갑니다.

## 2. 목표

Rust 재생 엔진 하나가 모든 믹스 레이어와 반주를 **같은 출력 callback에서 샘플 단위로** 섞습니다. 곡 시각은 그 엔진의 출력 프레임이 기준이 됩니다. JS는 명령을 보내고 위치를 읽는 화면이 됩니다. 녹음은 계속 DI만, 판정도 DI입니다.

## 3. 어려운 점

1. **MP3 반주**: Rust에 MP3 디코더가 없습니다. 새 의존성이 필요합니다(예: `symphonia` 순수 Rust, MPL-2.0. 배포 고지 절차 필요). 아니면 MP3일 때만 WebView 경로를 남깁니다.
2. **0.5~1.5배 연습 속도(음정 유지)**: 지금은 브라우저의 `preservesPitch`가 해 줍니다. Rust에서는 time-stretch가 필요합니다. 외부 라이브러리(C++ 포함 가능)를 쓰거나 WSOLA를 직접 구현해야 하고, 품질 확인은 사람 몫입니다. 가장 큰 작업입니다.
3. **출력 stream 분리**: 지금 모니터 출력은 입력 stream 세대에 묶여 있습니다. 입력 없이 재생만 하려면 "재생 출력 엔진"을 따로 두고, 입력 모니터가 그 엔진에 합류하는 구조로 바꿔야 합니다(`monitor.rs` 큰 수정).
4. **메모리**: 10분 stereo 반주를 f32로 풀면 약 230MB입니다. 믹스 준비 예산 512MiB에 반주가 들어가야 합니다.
5. **YouTube**: 외부 플레이어라 옮길 수 없습니다. YouTube 반주일 때는 지금 방식을 유지합니다.

## 4. 단계안(권장)

| 단계 | 내용 | 끝나면 |
| --- | --- | --- |
| R1 재생 출력 엔진 | 입력과 독립된 CPAL 출력 엔진. 입력 모니터는 이 엔진에 합류. 2B 클립 재생을 여기로 옮김 | 입력 없이도 Rust로 소리를 냄, 기존 모니터 동작 유지 |
| R2 1배속 네이티브 믹스 | WAV 반주·TAKE·Freeze·STEM·IMPORTED_STEM·RENDER를 Rust가 섞음(음량·mute·solo·재생·정지·seek·구간 반복). 곡 시각=출력 프레임. JS `PlayerEngine`에 "네이티브 모드" | 1배속 WAV 반주에서 모든 레이어 샘플 단위 동기 |
| R3 메트로놈·카운트인·녹음 정렬 | 클릭을 Rust에서 생성, 녹음 기준점을 출력 프레임으로 | 녹음 정렬이 JS 시각 의존에서 벗어남 |
| R4 MP3 | 디코더 의존성 추가(결정 필요) | MP3 반주도 네이티브 |
| R5 속도 변경 | time-stretch(결정 필요) | 0.5~1.5배도 네이티브 |

R4·R5 전에는 **MP3 반주이거나 1배속이 아니면 지금 WebView 경로로 자동 전환**합니다(기능 손실 없음). 네이티브 모드가 실패하면 같은 방식으로 되돌아갑니다.

## 5A. R1 구현 계획(2026-11-10)

R1은 화면에 아직 연결하지 않는 Rust 쪽 바탕입니다(화면 연결은 R2).

1. **재생 버스**(`src-tauri/src/audio/playback_bus.rs`, 순수 로직): stereo 보이스 여러 개(엔진 샘플레이트로 미리 맞춘 `Arc<[f32]>` 좌우, 곡 위의 시작 프레임, 음량), 재생·정지·이동·구간 반복, 현재 곡 프레임을 atomic으로 공개. 출력 callback에서 할당·잠금·해제를 하지 않습니다. 바뀐 보이스 묶음은 제어 쪽이 사본을 들고 있다가 callback이 놓은 뒤 해제합니다(2B `monitor_playback`과 같은 방식).
2. **입력 없는 출력**: 모니터 출력 stream을 입력 없이도 열 수 있게 합니다(재생만). 입력 모니터를 켜고 끌 때는 stream을 다시 만들고, 제어 쪽이 가진 보이스 묶음·위치·재생 상태로 버스를 새로 만들어 이어 갑니다(수십 ms 끊김 허용. callback 안에서 AmpliTube 삽입을 해제하지 않기 위함). 샘플레이트가 바뀌면 보이스를 다시 불러오라는 오류를 냅니다.
3. **출력 합성**: 버스 소리는 삽입(AmpliTube) 뒤에 더하고 자기 음량을 씁니다. 모니터 음량·Bypass와 무관합니다.
4. IPC 명령은 R2에서 화면과 함께 정합니다. R1은 Rust 단위 테스트로 검증합니다.

## 6. 바뀌지 않는 것

- 녹음 파일은 DI만, 판정 입력도 DI, 원본 파일은 읽기만 합니다.
- DB·MixDocument 저장 형식은 R1~R3에서 바꾸지 않습니다(IPC 명령만 추가).
- 실시간 AmpliTube는 인스턴스 하나(D3) 그대로입니다. 트랙별 다른 실시간 톤은 이 설계 범위 밖입니다.

## 7. R4 MP3 설계(2026-11-11, 결정 대기)

2026-11-10 결정은 "MP3는 계속 WebView"였습니다. 사용자가 R4 설계를 다시 요청해 선택지를 정리합니다. 결정 전에는 구현하지 않습니다.

### 지금 상태

- 반주 업로드는 WAV·MP3를 받습니다(`storage/projects.rs` 확장자·첫 바이트 확인).
- Rust 믹서 디코더(`mixer/pcm.rs`)는 WAV만 읽습니다. MP3 반주가 있으면 **네이티브 재생은 WebView로 넘어가고, WAV 믹스 내보내기는 `MIX_FORMAT_UNSUPPORTED`로 실패**합니다(화면 문구 "MP3 등 WAV가 아닌 음원").
- 따라서 R4는 재생뿐 아니라 "MP3 반주가 있는 믹스를 WAV로 내보내기"도 함께 해결합니다(같은 디코더를 씀).

### 디코더 선택지

| 안 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A `symphonia`(권장) | 순수 Rust 디코더. `default-features = false`, `mp3` 기능만(코어·mp3·메타데이터 crate 수 개) | C 코드·DLL 없음, Windows 판본과 무관, LAME 헤더의 앞뒤 무음(gapless) 정보 처리 | 새 의존성. **MPL-2.0**이라 이미 있는 MPL 6개와 같은 절차(배포 고지 + `sources/` 원본 보관, `docs/release/README.md`)를 따라야 함 |
| B Windows Media Foundation | OS 내장 디코더를 `windows` crate로 호출 | 새 라이선스 없음 | Windows N 판본엔 미디어 기능이 없어 실패할 수 있음, COM 초기화·스레드 관리 코드가 큼, 결과가 OS 버전마다 다를 수 있음 |
| C 계속 WebView(현 결정) | 바꾸지 않음 | 작업·의존성 없음 | MP3 반주는 샘플 단위 동기·Rust 메트로놈 기준점을 못 씀, MP3 반주 믹스는 WAV로 못 내보냄 |

MP3 특허는 2017년에 모두 만료되어 디코더 배포에 특허 문제는 없습니다.

### A안 구현 범위(결정되면)

1. `mixer/pcm.rs`: 확장자가 아니라 첫 바이트(기존 판정과 같음)로 MP3를 골라 `symphonia`로 풀고, 결과는 지금 WAV와 같은 `Pcm`(mono 또는 좌우 분리)으로 돌려줍니다.
   - MP3는 풀기 전엔 길이를 모르므로, **조각마다 예산(512MiB)과 길이(611초)를 확인**하고 넘으면 바로 `MIX_LIMIT_EXCEEDED`로 멈춥니다(256MiB MP3 업로드도 메모리 폭주 없음). 취소 확인도 조각마다 합니다.
   - 깨진 프레임은 건너뛰지 않고 실패로 처리합니다(무음이 끼어 싱크가 밀리는 것을 숨기지 않음).
2. 네이티브 재생: 화면의 "MP3면 WebView" 분기를 없앱니다(`useProjectMix`). 실패하면 지금처럼 WebView로 자동 전환합니다.
3. WAV 믹스 내보내기·DAW 표시: 같은 디코더로 MP3 반주를 받습니다. `docs/12` 믹스 계약의 "WAV만" 문구를 갱신합니다.
4. 배포 고지: 인벤토리·고지·`sources/` 원본 보관·`SOURCE-ACCESS` 갱신(`scripts/third_party_notices.mjs`).

### 싱크 위험과 확인 방법(핵심)

- MP3는 인코더가 앞에 무음(보통 약 1,105샘플, 44.1kHz에서 약 25ms)을 넣습니다. 기존 싱크 지점·녹음 정렬은 **WebView2가 MP3를 재생한 시각**을 기준으로 저장돼 있습니다. Rust 디코더가 이 앞 무음을 WebView와 다르게 처리하면, 기존 MP3 프로젝트의 테이크가 그만큼 어긋납니다.
- 방침: **WebView2와 같은 시작점**을 맞춥니다. 구현 첫 단계에서 실측합니다.
  1. 클릭 하나가 든 WAV를 만들고, 사용자 PC에 이미 있는 ffmpeg(libmp3lame)로 LAME 헤더가 있는 MP3와 없는 MP3를 만듭니다(작업 폴더, 저장소에 넣지 않음).
  2. 같은 파일을 검증앱 WebView2(CDP)와 Rust 디코더로 풀어 클릭 위치를 비교합니다.
  3. 1샘플 단위로 같지 않으면 차이를 보정하는 규칙을 정하고, 그 규칙을 회귀 검사로 고정합니다.
- 실측에서 맞출 수 없는 경우(예: 헤더 없는 MP3에서 WebView 동작이 일정하지 않음)엔 그 파일만 WebView 경로로 남깁니다.

### 다른 위험

- 44.1kHz MP3는 48kHz 출력으로 바꿀 때 지금의 선형 보간을 씁니다. WebView의 고품질 변환보다 고음이 약간 거칠어질 수 있습니다(44.1kHz WAV 반주도 R2부터 같은 상태). 청취에서 거슬리면 고품질 리샘플러는 따로 결정합니다.
- 디코딩 시간: 10분 MP3를 푸는 데 수 초가 걸릴 수 있습니다. 믹스 준비는 이미 작업 표시·취소가 있어 그 안에서 처리합니다.

### 결정할 것

1. 디코더: A `symphonia`(MPL-2.0) / B Windows Media Foundation / C 계속 WebView.
2. 범위: 네이티브 재생 + WAV 믹스 내보내기 함께(권장) / 네이티브 재생만.

### 결정(2026-11-11 사용자)

1. 디코더: **A `symphonia`**(2026-11-10의 "계속 WebView" 결정을 대신함).
2. 범위: **네이티브 재생 + WAV 믹스 내보내기 함께**.

## 8. R5 속도 변경 설계(2026-11-11, 결정 대기)

2026-11-10 결정("R5는 나중에 따로 설계")에 따라 사용자 요청으로 설계합니다. 결정 전에는 구현하지 않습니다.

### 지금 상태

- 배속(0.5~1.5배)은 WebView `<audio>`의 `playbackRate` + `preservesPitch`가 처리합니다. Chromium은 이를 **WSOLA**(파형 겹쳐 붙이기) 방식으로 구현합니다.
- Rust 재생은 1배속만 지원해, 배속을 바꾸면 `PlayerEngine.setRate`가 네이티브를 떼고 WebView로 돌아갑니다(`NATIVE_RATE_UNSUPPORTED`). AmpliTube 재생(모니터 경로 테이크)도 1배속만 지원합니다(`TakeMixPlayer.dropWet`).
- 배속으로 녹음한 테이크는 `transport.rate`를 저장하고, 곡 위치 = 시작 + 테이크 시각 × rate로 환산합니다. Rust 믹스 준비·WAV 내보내기는 이런 테이크를 `MIX_RATE_UNSUPPORTED`로 거부합니다.

### 엔진 선택지

| 안 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A `signalsmith-stretch`(권장) | Signalsmith Stretch(C++ 헤더 라이브러리, MIT)의 Rust 래퍼 crate(MIT). 빌드 때 C++을 함께 컴파일 | 음질이 좋음(Qt Multimedia도 채택), MIT라 고지만 추가, 피치 보존 품질이 WSOLA보다 화음·기타에 유리 | C++ 컴파일 단계 추가(MSVC는 이미 있음), 래퍼 crate가 0.1.x로 작음(필요하면 래퍼를 직접 유지), CPU가 WSOLA보다 큼 |
| B 자체 WSOLA | 지금 WebView와 같은 방식을 Rust로 직접 구현(외부 의존성 없음, 약 300줄) | 의존성·라이선스 없음, 지금 들리는 배속 음질과 비슷 | 음질이 지금보다 좋아지지 않음, 화음·잔향에서 떨림 소리, 직접 만든 DSP를 검증할 부담 |
| C 계속 WebView(현 상태) | 바꾸지 않음 | 작업 없음 | 배속 중엔 샘플 단위 동기·Rust 메트로놈 기준점을 못 씀 |

참고로 순수 Rust `timestretch` crate(위상 보코더+WSOLA 혼합)는 버전이 빠르게 바뀌는 중(0.1→0.9)이라 후보에서 뺐습니다. Bungee(MPL-2.0 C++)는 쓸 만한 Rust 래퍼가 없습니다. Rubber Band는 GPL/상용이라 제외합니다.

### 구조(A·B 공통)

1. **섞은 뒤 늘리기**: 레이어를 지금처럼 1배속 곡 시각으로 섞은 결과(stereo) 하나만 늘입니다. 레이어마다 늘이지 않으므로 CPU가 레이어 수와 무관하고 레이어끼리 어긋날 일이 없습니다. 음량·mute·solo 변경은 늘이기 지연(수십 ms)만큼 늦게 들립니다.
2. **별도 스레드**: 늘이기는 출력 callback이 아니라 AmpliTube 삽입과 같은 패턴의 작업 스레드에서 하고, 결과를 잠금 없는 링으로 callback에 넘깁니다(callback 할당·잠금 금지 규칙 유지). 1배속이면 늘이기를 거치지 않고 지금 경로 그대로입니다(1배속 동작·지연 불변).
3. **곡 시각**: 곡 위치는 늘이기에 넣은 입력 프레임 수로 셉니다. 기준점(R3)은 "장치에서 들리는 시각 ↔ 곡 프레임"에 늘이기 지연(입력 쪽 프레임)을 빼서 공개하고, `song_ms_at`은 경과 시간 × rate로 외삽합니다. 화면의 `NativeTransport.timeMs()`도 경과 × rate로 바꿉니다.
4. **이동·배속 변경·구간 반복**: 이동·배속 변경 때는 늘이기 상태를 비우고 새 위치부터 다시 채웁니다(첫 소리까지 수십 ms, WebView도 비슷). 구간 끝 되감기는 입력 쪽에서 이어 붙여 끊김 없이 넘어갑니다.
5. **메트로놈·카운트인**: 클릭은 늘이지 않고 출력 쪽에서 곡 시각에 맞춰 냅니다(박 간격 = 1배속 간격 / rate). 클릭이 늘어져 뭉개지지 않습니다.
6. **녹음 정렬**: 배속 중 녹음은 지금처럼 `transport.rate`를 저장하고, 기준점은 3의 곡 시각을 씁니다.
7. **AmpliTube 재생**: 모니터 경로 테이크 재생은 이번 범위에서도 1배속만(지금과 같음).
8. **실패하면** 지금처럼 WebView로 자동 전환합니다.

### 검사 계획

- 자동: 0.5·0.75·1.25·1.5배에서 출력 N프레임 뒤 곡 위치 ≈ N × rate(늘이기 지연 보정 후 1ms 안), 이동 뒤 첫 클릭 위치, 구간 반복 경계에서 위치 연속, 메트로놈 박 간격, callback 무할당(기존 검사 방식).
- 실측: 같은 반주를 0.75배로 WebView와 Rust에서 재생해 위치 차이 측정(무음 장치).
- 사람: 음질 비교(MANUAL-CHECKS에 추가).

### 결정할 것

1. 엔진: A `signalsmith-stretch` / B 자체 WSOLA / C 계속 WebView.
2. 배속으로 **녹음한** 테이크(`transport.rate≠1`)가 든 믹스: 이번엔 지금처럼 WebView로 넘김(권장, 단계 분리) / 이번에 함께(그 레이어만 따로 늘여 1배속 곡 시각에 맞춤, 작업·검사 범위가 큼).

### 결정(2026-11-11 사용자)

1. 엔진: **A `signalsmith-stretch`**.
2. 배속으로 녹음한 테이크가 든 믹스: **이번엔 WebView로**(1배속 녹음 자료만 Rust 배속 재생).
3. 빌드 방식(같은 날 추가 결정): 래퍼 crate `signalsmith-stretch`는 빌드 때 LLVM(libclang)을, `ssstretch`는 MSVC에서 컴파일 실패라, **C++ 원본(Stretch 1.4.0·Linear 0.6.4, MIT)을 `src-tauri/vendor/signalsmith`에 넣고 C 래퍼를 직접 만들어 `cc`로 컴파일**합니다. 원본 헤더는 수정하지 않습니다.

## 9. R6 배속 녹음 테이크의 Rust 재생 설계(2026-11-11)

R5 결정 2("배속으로 녹음한 테이크가 든 믹스는 이번엔 WebView로")의 후속입니다. 사용자 요청으로 설계하며, 결정 전에는 구현하지 않습니다.

### 지금 상태

- 0.75배로 연습하며 녹음한 테이크는 실제 시간으로 녹음되어 `transport.rate=0.75`가 저장됩니다. 테이크 프레임 f의 곡 위치는 `songStartMs + f/sampleRate×1000×rate + alignmentOffsetMs`입니다. 곡 시각으로 보면 테이크 길이는 녹음 길이 × rate입니다.
- WebView 재생(`TakeMixPlayer`)은 그 테이크를 `playbackRate = 지금 배속 / 녹음 배속`, 음높이 유지로 재생합니다. 녹음한 배속 그대로 들으면 원본이 그대로 나옵니다(변환 없음).
- Rust 믹스 준비와 WAV 내보내기는 `layer_source`(`mixer/render.rs`)에서 TAKE·RENDER의 `transport.rate≠1`을 `MIX_RATE_UNSUPPORTED`로 거부합니다. 그래서 그런 테이크가 하나라도 있으면 믹스 전체가 WebView로 넘어갑니다(샘플 단위 동기·Rust 메트로놈을 못 씀).
- Freeze 캐시(AmpliTube 처리 결과)와 Bounce(RENDER)도 테이크 시간축이라 같은 환산이 필요합니다. AmpliTube 실시간 재생(모니터 경로)은 지금처럼 1배속만입니다.

### 방식 선택지

### B안 구조(결정되면)

1. **준비**: `layer_source`의 거부를 없애고, 보이스에 `recorded_rate`(기본 1)를 붙입니다. 시작 프레임은 지금 규칙(곡 시각)을 그대로 씁니다.
2. **보이스 나누기**: `recorded_rate=1`인 보이스는 지금처럼 섞은 뒤 한 번 늘입니다(R5). 배속 테이크는 각자 늘이기 하나를 갖고, 출력 j프레임에 곡 위치 `start + j×p`가 오도록 테이크 시간축 입력(`(곡 위치 − 시작)/r`)을 비율 p/r로 넣습니다. R5의 `outputSeek` 정렬을 테이크마다 같은 식으로 씁니다.
3. **경로 선택**: 배속 테이크가 없으면 지금과 똑같습니다(1배속은 직접 경로). 있으면 1배속에서도 작업 스레드 경로로 재생합니다. p/r=1인 테이크는 늘이기 없이 샘플을 그대로 더합니다.
4. **이동·구간 반복·배속 변경**: 세대가 바뀌면 테이크별 늘이기도 함께 비우고 새 위치에서 다시 채웁니다. 구간 경계에서는 테이크 입력도 되감기 위치에서 이어 붙입니다(R5 `fill_input`과 같은 방식).
5. **Freeze·RENDER**: 원본 테이크의 `transport.rate`를 그대로 따릅니다(같은 시간축).
6. **WAV 내보내기**: 결정 2에 따릅니다.
7. **실패하면** 지금처럼 WebView로 넘어갑니다.

### 검사 계획

- 자동:
  - 0.5배로 녹음한 클릭 테이크를 p = 0.5·0.75·1·1.5배로 재생할 때, 클릭이 곡 위치에 맞는지(1ms 안).
  - p=r이면 출력이 원본 샘플과 같은지.
  - 1배속 녹음 레이어와 함께 섞었을 때 두 레이어의 클릭이 서로 맞는지.
  - 이동·구간 반복 뒤의 위치, 배속 테이크 여러 개의 성능(무시 표시 측정 검사).
- 실측: 무음 가상 출력으로 같은 믹스를 WebView와 Rust에서 재생해 위치 차이를 잽니다.
- 사람: 녹음 배속 그대로·다른 배속으로 들었을 때의 음질과 박 맞음(MANUAL-CHECKS에 추가).
